# Banc de mesures (phase 1) : plan de mise en œuvre

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** un banc qui rejoue l'usage réel (10 sessions mixtes et plus) sous
Linux et sous Windows, compare deux versions sur la même machine, garde la CI
contre les régressions et pose la ligne de base 0.16.0.

**Architecture :** les scénarios sont des spécifications WebdriverIO dans
`e2e/banc/`, pilotées par le harnais existant (`e2e/wdio.conf.js`), qui
reçoit le chemin du binaire à mesurer. Chaque scénario verse des
**échantillons bruts** dans un JSON commun. Un comparateur Node calcule les
statistiques et le verdict. Un lanceur Node multiplateforme construit deux
références dans des `git worktree` et les fait tourner en alternance.

**Tech Stack :** Node 22 (ESM, `node:test`), WebdriverIO (harnais existant),
Rust (exemples du cœur, tests ignorés), GitHub Actions.

**Spec :** `docs/superpowers/specs/2026-11-27-banc-et-audit-design.md`

## Global Constraints

- Tout en français : code, commentaires, noms de tests, commits. Pas de tirets
  cadratins dans la prose.
- `./check.sh` vert avant chaque commit ; PR ; `gh pr checks` vert ligne à ligne
  avant fusion ; pousser sur `github` et `gitlab`.
- La fonctionnalité `webdriver` seulement sous Windows (harnais embarqué), et
  jamais dans un binaire qui quitte la machine qui l'a construit : pas
  d'artefact de CI qui la contienne.
- On mesure le **profil release publié** (`cargo build --release`), sans
  profil allégé.
- Pas de nouvelle dépendance npm ni cargo, sauf justification passée par
  `cargo deny` et `npm audit`.
- Actions GitHub épinglées sur leur commit (`uses: o/a@<sha> # vX.Y.Z`),
  `permissions` minimales.
- Mesures hors Wayland (déjà fait par le harnais), `~/.cache` présent dans le
  bac à sable (déjà fait), machine au repos (charge moyenne sous 4 au départ,
  sinon refus).
- Aucun secret dans un fichier suivi : les identifiants de la VM et du parc
  xrdp passent par l'environnement (`BANC_RDP_WINDOWS`, `BANC_XRDP`), jamais
  écrits dans le dépôt.
- Les résultats JSON restent hors du dépôt (`e2e/banc/resultats/` dans
  `.gitignore`). Seules les lignes de base en Markdown sont consignées.
- La 0.16.0 est la plus vieille référence prise en charge.

## Review Focus

1. **Un binaire de référence plus ancien qui n'a pas un sélecteur du harnais de
   `HEAD`.** Le scénario concerné doit être marqué « absent » pour cette
   référence, pas faire échouer tout le banc. Testé dans la tâche 2
   (métrique présente d'un seul côté) et la tâche 9 (scénario en échec
   consigné).
2. **Un processus qui meurt pendant la mesure** (sidecar RDP, WebView2). Le
   relevé mémoire et processeur ne doit ni planter ni compter zéro : il
   marque l'échantillon manquant. Testé dans la tâche 1.
3. **Une métrique à variance nulle ou à médiane nulle** (0 ms, toujours
   25 i/s). L'écart relatif ne doit pas diviser par zéro ni déclarer une
   régression sur du bruit d'arrondi. Testé dans la tâche 2.
4. **Une machine chargée** au lancement ou pendant la mesure. Le lanceur
   refuse au départ et consigne la charge à la fin, et le comparateur
   l'affiche. Testé dans la tâche 9.
5. **Windows et ses processus `msedgewebview2.exe`**, partagés avec Edge s'il
   est ouvert. Le relevé ne compte que les descendants de l'application.
   Testé dans la tâche 1 (filtrage par arbre de processus).

- Modify : `check.sh` (lancer `node --test scripts/tests/banc-*.test.mjs`, à
  côté des autres gardes `.mjs`)

**Interfaces :**
- Produces :
  - `stats(valeurs: number[]) -> {n, mediane, p25, p75, p95, min, max}`. Les
    valeurs `null` sont ignorées ; si la liste est vide, le résultat est `null`.
  - `arbreDeProcessus(racinePid: number) -> Promise<number[]>` : la racine et
    tous ses descendants, sous Linux par `/proc/*/stat` (champ ppid), sous
    Windows par `Get-CimInstance Win32_Process` (ParentProcessId).
  - `releveProcessus(pids: number[]) -> Promise<{memoireMo: number|null,
    processeurS: number|null, vivants: number}>`. La mémoire se mesure sous
    Linux en PSS (`/proc/<pid>/smaps_rollup`), et sous Windows en working set
    privé (`Get-Process` → `PrivateMemorySize64`). Le temps processeur est
    cumulé. Un PID disparu est ignoré (`vivants` le dit), et si aucun n'est
    vivant le résultat vaut `null`.
  - `nouveauResultat({reference, commit, plateforme}) -> Resultat` et
    `ajouter(resultat, cle: string, {unite, sens: "bas"|"haut"}, echantillons: number[])`.
    Ce dernier concatène si la clé existe déjà.
  - `ecrireResultat(resultat, chemin)` et `lireResultat(chemin) -> Resultat`.
  - Le format `Resultat` :
    `{schema: 1, reference, commit, plateforme, machine: {processeur, coeurs, memoireGo, chargeDepart, chargeFin}, date, metriques: {[cle]: {unite, sens, echantillons: number[]}}, absents: string[]}`.
  - Les clés suivent la forme `"S<n>/<nom>"`, par exemple `"S2/echo-1-session"`.

  - `ajouter` deux fois sur la même clé concatène les échantillons.
  - Un aller-retour `ecrireResultat` puis `lireResultat` est identique.
  - `releveProcessus([999999999])` (PID inexistant) donne

  - `releveProcessus([process.pid])` donne `vivants === 1` et `memoireMo > 0`.

### Task 2 : comparateur

**Files :**
- Create : `e2e/banc/comparer.js` (module, et CLI par
  `node e2e/banc/comparer.js <a.json> <b.json> [--seuils e2e/banc/seuils.json] [--markdown sortie.md]`)
- Create : `e2e/banc/seuils.json`
- Create : `scripts/tests/banc-comparer.test.mjs`

**Interfaces :**
- Consumes : `stats`, `lireResultat` (tâche 1).
- Produces :
  - `comparer(a: Resultat, b: Resultat, seuils) -> Ligne[]`, où
    `Ligne = {cle, unite, a: Stats|null, b: Stats|null, ecart: number|null, verdict: "mieux"|"pire"|"bruit"|"absent", garde: boolean}`.
  - `enMarkdown(lignes, a, b) -> string`.
  - Code de sortie de la CLI : 1 si une ligne a `verdict === "pire"` **et**
    `garde === true`, sinon 0.
  - Le format de `seuils.json` est
    `{defaut: {seuil: 0.10}, metriques: {[cle]: {seuil?: number, garde?: boolean}}}`.

Règle du verdict :
- `ecart = (mb − ma) / max(|ma|, plancher)`, où `plancher` vaut 1 unité (ms,
  Mo, i/s). Il évite la division par zéro.
- Le signe est inversé quand `sens === "haut"`, pour que `ecart > 0` veuille
  toujours dire « pire ».
- Le verdict est `bruit` si les intervalles `[p25, p75]` se chevauchent **ou**
  si `|ecart| < seuil`. Sinon c'est `pire` (ecart > 0) ou `mieux`.
- Il est `absent` si la clé manque d'un côté ou si l'un des côtés a moins de
  3 échantillons.

- [ ] **Step 1 : tests qui échouent** :
  - Latence de 10 ms à 13 ms, sens `bas`, sans chevauchement : verdict `pire`,
    écart ≈ 0,30.
  - i/s de 25 à 20, sens `haut` : verdict `pire`.
  - Échantillons `[10, 11, 12]` contre `[11, 12, 13]` (chevauchement) :
    verdict `bruit`.
  - `0` contre `0` : verdict `bruit`, pas de `NaN`.
  - Clé présente seulement dans `b` : verdict `absent`.
  - Ligne `pire` avec `garde: false` : la CLI sort 0. Avec `garde: true`, elle
    sort 1.
  - `enMarkdown` contient une ligne par clé et la charge de départ et de fin
    des deux machines.
- [ ] **Step 2 :** `node --test scripts/tests/banc-comparer.test.mjs`. Attendu : ÉCHEC.
- [ ] **Step 3 :** implémenter. `seuils.json` démarre avec `defaut.seuil = 0.10`
  et aucune garde. Les gardes se posent à la tâche 10, après calibration.
- [ ] **Step 4 :** tests verts.
- [ ] **Step 5 :** commit `test(banc): comparateur de deux résultats avec verdict tenant compte du bruit`.
